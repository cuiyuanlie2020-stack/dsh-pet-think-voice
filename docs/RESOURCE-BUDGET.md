## 1. 结论摘要

**一句话：这个插件在稳态下是"陪衬级"负载——约 0.26 个 CPU 核心、约 1 个百分点的 GPU、约 30MB 内存、显存占用 < 100MB 且不驻留任何模型权重，不朗读时网络流量为 0。**

| 指标 | 实测值 | 性质 | 对主力负载的影响 |
|---|---|---|---|
| **显存（VRAM）** | **≤ 100MB**（贴图 26.6MB 推算 + 三轮实测 18/47/−110MB） | 常驻（浏览器纹理） | 可忽略 |
| **GPU 利用率** | **+0.6 ~ 2.5 个百分点** | 稳态（仅 60fps 合成） | 噪声级 |
| **CPU** | **0.26 个核心**（= 24 核的 1.1%） | 稳态（仅渲染时） | 小；低配机占比上升 |
| **内存** | host **+2.5MB**；浏览器 JS 堆 **+25~29MB** | 常驻 | 可忽略 |
| **网络** | 朗读时 ~30KB/句；不朗读 **0** | 事件驱动 | 见 5.1 |
| **磁盘** | 整包 **4.54MB**（tar.gz） | 一次性 | 可忽略 |
| **帧率影响** | **不掉帧**（58.7 → 58.6 fps） | 稳态 | 无 |

**最关键的结论（直接回答"会不会跟我的本地模型抢资源"）：**

- ❌ **不抢显存**：插件自身**没有任何模型权重**（TTS 走云端），显存只用来放 Live2D 贴图，**≤100MB**。相比之下 minimax-h3 / qwen-image-2.1 吃的是 GB 级。
- ⚠️ **唯一真实竞争点是 CPU**（0.26 核）——这在大核数机器上是 1%，在 4~6 核老机器上会到 4~6%，**所以 DESIGN 里的"负载闸"是必要的，不是摆设**。

## 3. 测量方法（三件套）

| 脚本 | 测什么 | 手段 |
|---|---|---|
| `bench/host_probe.js` | 插件 host 半区常驻开销（HTTP + SSE + 推帧） | 自建 Node 服务复刻 host 形态，用 `process.memoryUsage()` / `process.cpuUsage()` 自报 |
| `bench/resource_probe.py` | Edge TTS 单次合成的墙钟 / CPU / 音频体积 / RSS | `psutil` 读本进程 CPU 与 RSS + `edge_tts` 流式计数 |
| `bench/resource_probe2.py` | 「Python 边车」方案的冷启动代价 | 子进程**自报**峰值 RSS（避免父进程采样失真） |
| `bench/serve.js` + `bench/index.html` + `bench/sample.py` + `bench/analyze.py` | 浏览器侧 Live2D 开销 | ① 用**上游真实资产**（`live2d-vendor.js` + `ds-whale-girl` 模型 + 官方 Cubism Core）在真浏览器里渲染；② `psutil` 采 Edge 全进程 CPU/RSS + `nvidia-smi` 采 GPU；③ 页面内 `ticker` 首尾插桩测**每帧主线程工作量**；④ `analyze.py` 把页面时间轴与系统采样对齐 |

**方法学要点（重要，避免误读）：**

1. **每帧工作量用页面内计时，不用进程求和**——因为 Edge 的进程数会变（测时 22 → 17），进程求和法在进程退出时会把已累计的 CPU 一起丢掉，导致数值可能"下降"。页面内插桩不受此影响。
2. **两法互证**：页面内计时得出的 0.26 核 与 进程求和法得出的 0.256 核**吻合到 2%**，故该结论可信。
3. **Windows CPU 计时精度为 15.6ms**，故"0ms"应读作"< 15.6ms"，不是"绝对零"。
4. 浏览器侧用 `headless=new` + `--enable-gpu`，已通过 `WEBGL_debug_renderer_info` 确认走的是**真 GPU**（NVIDIA D3D11），不是软件渲染。

## 4. 分项实测

### 4.1 插件 host 半区（Node，常驻）

复刻形态：HTTP 路由 + 同源 SSE 长连接 + 每 1s 推帧 + 每 5s 一次音频回传，持续 20.5s。

| 时点 | RSS | 堆 | external | 累计 CPU |
|---|---|---|---|---|
| 进程启动（未起服务） | 44.4 MB | 5.3 MB | 1.9 MB | 108 ms |
| 服务已起（SSE 空闲） | 46.7 MB | 5.2 MB | 2.0 MB | 124 ms |
| SSE 客户端已连 | 47.9 MB | 5.3 MB | 2.0 MB | 124 ms |
| 5s / 10s / 15s | 47.9 / 46.5 / 46.8 MB | 5.4 / 5.2 / 5.4 MB | — | 124 ms |
| **20.5s 结束** | **46.9 MB** | 5.5 MB | 2.2 MB | **124 ms** |

**读数：**

- **边际内存 = +2.5MB**（46.9 − 44.4）。44.4MB 是 Node 运行时本身的成本，DSH 已经在付，**插件只多付 2.5MB**。
- **边际 CPU ≈ 0**：20.5s 内 CPU 从 124ms 增长到 124ms（**低于 15.6ms 计时精度**）。平均占用率 < 0.1% 单核。
- 内存**无增长趋势**（5.4→5.5MB 堆），20s 内无泄漏迹象。

> ⚠️ 这是**独立进程**的上界；真实插件跑在 DSH 的 Node 进程内，边际成本只会更小。

### 4.2 Edge TTS 单次合成

配置 `voice=zh-CN-XiaoyiNeural, pitch=+30Hz`；样本 = 6 条真实场景台词（14 / 33 / 25 / 25 / 33 / 139 字）。

| # | 字数 | 墙钟 | CPU | 音频 | 进程 RSS |
|---|---|---|---|---|---|
| 1（冷启动） | 14 | 0.96s | 31.2 ms | 16.0 KB | 64.1 MB |
| 2 | 33 | 1.03s | <15.6 ms | 30.1 KB | 64.1 MB |
| 3 | 25 | 1.02s | <15.6 ms | 30.5 KB | 64.5 MB |
| 4 | 25 | 0.97s | <15.6 ms | 26.7 KB | 64.8 MB |
| 5 | 33 | 0.96s | <15.6 ms | 30.9 KB | 65.2 MB |
| 6 | 139 | 1.19s | 31.2 ms | 134.6 KB | 65.4 MB |

**汇总：**

| 指标 | 值 |
|---|---|
| 墙钟 | 最小 0.96s / **中位 1.00s** / 最大 1.19s |
| 冷启动额外代价 | **≈ 0**（首句 0.96s，不慢于热态）—— 会话复用良好 |
| CPU | 中位 **< 15.6ms**（低于计时精度）；最大 31.2ms（计时单位的一跳） |
| 音频体积 | 中位 **30.3 KB**；短句 16KB；139 字长句 134.6KB |
| 进程 RSS | 61.6 → **65.4MB（+3.8MB）**，6 次调用无累积增长 |
| 吞吐 | **28.8 字/秒**；下行 **29.6 KB/秒** |

**读数：`Edge TTS 是"网络等待型"负载，不是"CPU 密集"型。**整句耗时约 1 秒基本全在等服务端返回，本地只花几十毫秒。**这就是它比本地 TTS 更适合做"陪衬"的根本原因。**

> ⚠️ 61.6MB 基线含 Python 解释器 + edge_tts 依赖；插件里这段跑在 Node 进程内，故应看**增量（+3.8MB）**，而非绝对值。

### 4.2b Node 侧零依赖实现（**插件实际采用的路径**，P0-2 实测）

> 背景：npm 上所有 Edge TTS 包（`edge-tts` / `msedge-tts` / `node-edge-tts` / `@andresaya/edge-tts` / `edge-tts-universal`）
> **全部依赖 `ws`**。而 DSH 的 Node 是 **24.18.1**，自带全局 `WebSocket`（undici，且支持 `headers` 选项）→ 协议可自实现，**插件零依赖**。
> 本节数据来自 `p0/p0-2-verify.mjs`；实现见 `p0/edge-tts-zerodep.mjs`。

| 指标 | 实测 |
|---|---|
| 冷启动（第 1 条） | **811 ms** |
| 热态墙钟均值 | **1261 ms** |
| **CPU / 次（中位）** | **16 ms** |
| CPU 合计（6 次） | 156 ms |
| 音频体积 | 中位 30.1 KB；130 字连读 118.8 KB |
| **进程 RSS 增量** | **+19.3 MB**（40.4 → 59.7） |
| 吞吐 | 22.2 字/秒 · 23.0 KB/秒 |
| npm 依赖 | **0 个** |

**与 Python 参考版的一致性（强交叉验证）**：

| 样本 | 零依赖 Node | Python `edge-tts` 参考版 |
|---|---|---|
| 「powersell 又想咬我了」 | 16,416 B | 16,416 B |
| 「哦——原来 param 是必填的…」 | 30,816 B | 30,816 B |
| 「等等，这个正则怎么写都不对…」 | 31,248 B | 31,248 B |
| 「嗯……这个 bug 藏得真深…」 | 27,360 B | 27,360 B |
| 「好，思路清晰了，let me…」 | 31,680 B | 31,680 B |
| 5 句连读（130 字） | 121,680 B | 121,680 B |

**6/6 字节数一致**（同格式 CBR 24kHz/48kbps，字节数一致 ⇒ 时长一致）。
补充：单样本解码后 PCM 比对 → 75.8% 采样点完全相同，最佳对齐 lag=0、**相关系数 0.99975**。

**两个"确定性"事实（避免误判验收判据）**：

1. **同一实现 → 逐字节可复现**：零依赖实现连跑两次 MD5 相同；Python 版连跑两次也相同。
2. **不同实现之间不是逐字节相同**（同为确定性但彼此不同），原因未完全定位，**无实际影响**。
   ⚠️ 因此**「与 Python 版逐字节相同」不是可用判据**；可用判据是「字节数/时长一致 + 解码后高相关 + ASR 可懂」，本次三项均满足。

> ⚠️ 与 4.2 的口径差异：RSS 增量 **+19.3MB（Node）** vs **+3.8MB（Python）**——Node 版多出的是 undici/WebSocket 机制开销。
> **但两者 CPU 都可忽略，"Edge TTS 是网络等待型负载"的结论不变。**
> 且插件里这段跑在 **DSH 自己的 Node 进程内**，属边际分配（大部分可 GC），不是独立进程常驻。


### 4.3 已放弃方案的成本对照：Python 边车

若 P0-2 证明 Node 侧无可用 Edge TTS 库，退路是"Node 桥接 Python 边车"。**先量清楚它的代价：**

| 指标 | 实测 |
|---|---|
| 空 Python 进程 | 墙钟 0.29~0.34s，RSS 37.6~37.9 MB |
| `import edge_tts` 后 | RSS 60.6~61.3 MB（**+23MB 纯依赖**） |
| 合成一句后 | RSS 63.2~63.9 MB |
| **全链路冷启动（spawn + import + 合成 1 句）** | **1.46 / 1.53 / 1.54s → 中位 1.53s** |

**读数：边车方案每句多付 +0.53s 冷启动 + 一个 64MB 的子进程。**
结论：这是可行退路（不违反 R1 显存红线），但会**明显拉长"≤3s 内播放"的余量**（G3），并让低配机多背 64MB。**优先级：能用 Node 库就不要边车。**

### 4.4 浏览器侧 Live2D 渲染

**测试方法**：用上游真实资产（`live2d-vendor.js` = pixi 8.19 + 引擎；`ds-whale-girl` 模型 3449×4628，缩放至铺满 480×480 画布；官方 Cubism Core 207KB），在真 Edge 里跑两个阶段：
- **阶段 1**：空舞台（仅 PIXI 渲染循环）10s
- **阶段 2**：装载真实 Live2D 模型 15s

| 指标 | 阶段 1 空舞台 | 阶段 2 +Live2D | **增量** |
|---|---|---|---|
| 帧率（60fps 封顶） | 58.7 fps | **58.6 fps** | **不掉帧** |
| **每帧主线程工作量** | 0.095 ms（p95 0.2） | **4.298 ms**（p95 9.6） | **+4.2 ms/帧** |
| → 折算单核占用 | — | — | **0.26 核** |
| 进程求和法 CPU（独立验证） | 24.8% 单核 | 50.4% 单核 | **+25.6 个百分点 = 0.256 核** ✅ 互证 |
| GPU 利用率（平均） | 0.6% | 1.2% | **+0.6 pp** |
| GPU 显存 | 2082 MB（全机） | 2101 MB（全机） | **+18 MB** |
| JS 堆 | — | 25~29 MB | — |
| Edge 全进程 RSS | 1020→1086 MB | 1202→968 MB | 见下注 |

**三轮 GPU 显存增量：+18 / +47 / −110 MB。** 波动范围说明：**它在 nvidia-smi 全机统计的噪声量级内，上界 < 100MB。**

**独立推算验证**：贴图 `2048×2048×4B + 1024×1024×4B = 20MB`，含 mipmap ×1.33 ≈ **26.6MB** —— 与实测吻合，佐证该量级可信。

**GPU 利用率三轮增量：+0.6 / +0.9 / +2.5 个百分点。** 取 **+0.6 ~ 2.5pp**（nvidia-smi 采样分辨率 1%，背景占用有波动）。

**极端冗余测试**：关掉帧率上限（`?fps=0`）跑到 **240fps**，Live2D 仍未掉帧（240.2 → 239.3 fps）。即当前负载只用了约 1/4 的余量。

> **注**：Edge 全进程 RSS 在阶段 2 反而下降，是**进程退出导致的统计口径变化**（22 → 17 个），不是内存真的释放。这也是第 3.1 条方法学要点的由来——**跨进程求和不可用于判断内存趋势**。

## 5. 典型场景推演

### 5.1 场景 A：vibecoding 稳态 1 小时（默认 **20s** 一句 —— D3 已定）

| 项 | 推算 | 依据 |
|---|---|---|
| 朗读句数 | **180 句/小时** | 3600s ÷ 20s |
| 下行流量 | **≈ 7.2 MB/小时** | 180 × 40KB（中位 30.3KB，长句至 134KB，取混合均值） |
| Edge 合成累计 CPU | **< 6 秒/小时**（≈0.15% 单核） | 180 × <31ms |
| host 常驻内存 | **+2.5 MB** | 4.1 实测 |
| 浏览器稳态 CPU | **0.26 核** | 4.4 实测（仅渲染，与朗读条数无关） |
| 浏览器稳态 GPU | **+1 pp 量级**；显存 **<100MB** | 4.4 实测 |

> ⚠️ **本节数字随 D3 变化**：2026-10-11 D3 由 30s 改为 **20s**，故句数 120→180、流量 4.8MB→7.2MB、合成 CPU <4s→<6s。
> 单向成本（40KB/句、<31ms/句、+2.5MB 常驻）为**实测值**，未重新测量；上表是按新频率**重算**的结果。

**→ 相当于"后台常驻一个轻量网页动画"。网络流量按 7.2MB/小时算，挂着 DSH 一天 8 小时约 58MB。**

### 5.2 场景 B：与本地大模型共存（用户最关心的场景）

本机基线：RTX 5070 Ti 16GB；测时全机显存占用 ~2.1GB（桌面等）。

| 主力负载 | 其显存占用 | 插件额外占用 | 竞争评估 |
|---|---|---|---|
| minimax-h3（视频生成，权重 99GB 级） | 吃满 16GB 是常态 | **≤100MB** | 无实质竞争 |
| qwen-image-2.1（文生图） | 8~12GB | **≤100MB** | 无实质竞争 |
| 本地 LLM（Ollama 等） | 数 GB | **≤100MB** | 无实质竞争 |
| — | — | **CPU 0.26 核** | ⚠️ **唯一真实竞争点** |

**结论：显存层面插件是"隐形"的；CPU 层面在 24 核机器上占 1%，低核数机器上占比上升——这正是 DESIGN 7.3「负载闸」存在的理由。**

> ⚠️ **另有一项与资源无关但同样重要的冲突**：插件会**发声**。用户跑主力任务时可能不希望被念思考打断——这属于 DESIGN 7.2 的"静默档"要覆盖的场景（也是 R5「可一键停」的动机）。

### 5.3 场景 C：8G 显存 / 16G 内存低配（发布目标）

| 指标 | 推算 | 是否达标（DESIGN 7.4） |
|---|---|---|
| 额外显存 | ≤100MB（关闭可选小模型时；贴图 26.6MB 为主） | ✅ ≤150MB |
| 额外 GPU 利用率 | 0.6~2.5 pp | ✅ ≤3 pp |
| 额外 CPU | 0.26 核 → 在 4~6 核机器上占 4~6% | ⚠️ 待实机复验（V4） |
| 额外内存 | host +2.5MB + 浏览器 JS 堆 25~29MB（+纹理解码约 10MB） | ✅ ≤80MB |
| 帧率影响 | 不掉帧（本机 240fps 仍有 4 倍余量） | ⚠️ 低配待验 |
| 前置条件 | 必须关闭"可选小模型打分"（那是唯一吃显存的环节） | 设计已默认关闭 |

### 5.4 场景 D：断网

| 项 | 行为 |
|---|---|
| Edge 合成 | 失败 → **降级为纯气泡文字**，留痕提示（红线 R3） |
| 插件占用 | 退化为 host 半区水平：**+2.5MB 内存、CPU ≈ 0、网络 0** |
| 形象 | 若 Cubism Core 未曾缓存，首次断网会拿不到运行时（V3 弱网后路） |

## 6. 预测项与不确定性（明确区分"测过"与"没测过"）

### 6.1 未测项（诚实列出）

| # | 未测 | 为什么 | 预测 / 处理 |
|---|---|---|---|
| 1 | **低配机（8G/16G）实机表现** | 本机是高配 | 预测达标（显存/内存差距巨大），但 CPU 占比可能上升 → **V4 复验** |
| 2 | **真实窗口（headful）vs headless** | 测的是 `headless=new` | 预测差异 <1pp（组件路径不同，但 WebGL 渲染成本一致）→ **V4 复验** |
| 3 | **模型播放动作（motion）时的开销** | 测的是 idle 状态 | 预测略高于 4.2ms/帧，但同量级 → P3 复测 |
| 4 | **高 DPI / 多显示器缩放** | 未测 | 预测随画布像素数近似线性变化 |
| 5 | ~~Node 侧 Edge TTS 库的实际内存~~ | ✅ **已测**（P0-2，见 4.2b） | **+19.3 MB RSS / CPU 中位 16 ms**（零依赖自实现） |
| 6 | **插件与 DSH 同进程的边际成本** | 无法在无 DSH 时分离测量 | 4.1 是**独立进程的上界**，同进程边际只会更小 |
| 7 | DSH Web GUI 自身的负载 | 它本来就开着，属既有成本 | 不计入插件 |
| 8 | Windows DWM 合成的额外开销 | 未单独隔离 | 含在 4.4 的"空舞台"基线里（故增量才是插件成本） |

### 6.2 测量本身的已知偏差

1. **进程求和法在进程退出时会低估 CPU** —— 故 4.4 的结论以页面内计时为准，进程求和仅作互证。
2. **nvidia-smi 的 GPU 利用率采样分辨率为 1%**，显存统计为全机口径（无法隔离到 Edge 进程，`--query-compute-apps` 不含图形进程）——故显存结论给的是"<100MB 上界"而非精确值。
3. **Windows CPU 计时精度 15.6ms**，"0ms" = "<15.6ms"。
4. 4.4 的 CPU 增量含浏览器为该画布付出的一切（合成、光栅化、可能的 GPU 进程转发），是"端到端增量"，偏保守。
